# 项目面试逐字稿

---

## 一、总体介绍

**我们这个项目叫做「AE Sentinel —— 药物临床试验不良事件智能监测平台」。简单说，就是给新药临床试验做"AI安全员"——自动识别患者用药后的不良反应是什么、有多严重、要不要紧急上报，还能主动发现安全隐患。**

过去这些事情全靠人做：医生在病历上写了"患者用药后头晕恶心"，药物警戒专员得一条条翻医学术语词典（MedDRA）去编码，一个三期临床试验可能产生上万条不良事件，人工处理又慢又容易出错。我们的系统用 AI 替代了这个繁琐过程。

---

## 二、业务背景介绍

> 如果你没接触过临床试验，下面几分钟帮你快速理解这个系统在解决什么问题。

### 2.1 什么是临床试验？

药厂研发一种新药，上市前必须做"临床试验"——招募几百到几千名患者，给他们用药，观察效果和安全。试验会分很多个周期，每个周期患者来医院做检查、抽血、填表，这叫"访视"。

### 2.2 什么是"不良事件"（AE）？

**患者用药后出现的任何不舒服，都叫不良事件**。比如头疼、恶心、皮疹、发烧，甚至严重的肺炎、肝损伤、死亡。不管是不是药物引起的，都算 AE。

### 2.3 什么是"严重不良事件"（SAE）？

如果 AE 导致了**死亡、危及生命、住院、残疾**，这类 AE 升级为 SAE。SAE 必须在**7天（死亡/危及生命）或15天（其他）**内上报药监局，超期就违规了。

### 2.4 什么是 MedDRA 编码？

MedDRA 是国际通用的医学术语词典，有 5 级层级结构（SOC → HLGT → HLT → PT → LLT）。比如患者说"感觉头晕恶心想吐"，需要编码成标准术语"恶心（Nausea）"，再往上归属到"胃肠系统疾病"这个大类。这个编码过程非常专业，不同编码员之间一致性常常不到 80%。

### 2.5 什么是方案偏离？

试验方案规定了每个访视必须在计划日期±3天内完成，必须做哪些检查。如果患者第 15 天没来，第 21 天才来——这就是"访视超窗"，属于方案偏离。大量偏离会影响试验数据的可信度。

### 2.6 我们的系统做了什么？

**用一句话总结：输入一段口语化的症状描述，自动输出标准化编码、严重性判定、SAE 报告、偏离预警、安全信号分析。** 把原来需要 5 个专业人员做的事情，让 5 个 AI 智能体自动协作完成。

## 三、数据来源介绍（系统用了哪些数据）

> 一个 AI 系统能不能用，数据是基础。下面讲清楚我们这个系统用了什么数据，从哪来的，怎么用的。

### 3.1 数据全景图

| 数据项 | 来源 | 费用 | 格式 | 在本系统中的用途 |
|--------|------|------|------|-----------------|
| MedDRA 术语库 | meddra.org 学术订阅 | 免费（非商业） | ASCII .asc | 智能体1：AE 标准编码 |
| FDA FAERS 数据 | fda.gov 公开下载 | 完全免费 | ASCII/ZIP | 智能体4：背景发生率估算 |
| PubMed 文献 | NCBI E-utilities API | 完全免费 | JSON/XML | 智能体4：同类药物安全性文献 |

| 模拟试验方案 | 自行设计（基于真实模板） | - | 结构化数据 | 预期AE列表、访视计划 |

### 3.2 MedDRA 术语库——编码的基础

MedDRA 是 ICH 发布的国际通用医学术语词典，包含 **5 级层级结构**：
```
SOC（27个系统器官分类，如"胃肠系统疾病"）
 └─ HLGT（约337个高位组术语）
     └─ HLT（约1,737个高位术语）
         └─ PT（约26,000+个首选术语，如"恶心"）
             └─ LLT（约85,000+个低位术语，如"反胃感"）
```
我们系统在 `data/docs/MedDRA_层级结构参考.md` 中整理了完整的 27 个 SOC 分类。MVP 阶段内置了 30+ 医学同义词映射表，覆盖临床试验中最常见的不良事件术语。

### 3.3 FDA FAERS——全世界最大的不良事件数据库

FAERS 是美国 FDA 维护的**公开不良事件报告数据库**，收集了 2004 年至今全球数百万份真实不良事件报告，每季度更新。

**数据文件结构（每季度 7 个表）**：
- `DEMO`：患者人口学信息（年龄、性别、体重）
- `DRUG`：药物信息（名称、剂量、适应症）
- `REAC`：不良反应（MedDRA 编码）
- `OUTC`：转归（死亡、住院、残疾等）
- `RPSR`：报告来源（报告人职业、国家）
- `THER`：治疗日期
- `INDI`：适应症

我们在 `data/downloads/` 下放了完整下载链接清单和自动下载脚本 `download_faers.py`，可一键下载指定季度的数据。

### 3.4 PubMed 文献——信号验证的依据

当智能体4 发现一个聚集性信号（比如 XK-001 用药组出现 3 例肝损伤），不能凭空说这是问题，需要用**已发表的文献**来佐证。PubMed 提供了 E-utilities API，可免费检索 3000 万+ 篇生物医学文献。

我们在 `data/docs/PubMed_文献检索参考.md` 中记录了 5 个真实 PMID 示例和检索策略，项目代码中内置了 NCBI API Key。

### 3.5 模拟数据与知识库文档

`data/docs/` 目录下存放了 6 个结构化参考文档，作为 RAG 知识库的基础语料：
- `CIOMS-I_参考文档.md`：CIOMS-I 报告 20+ 字段规范
- `ICH_GCP_安全性报告指南.md`：GCP 对 SAE 报告时限、研究者职责的要求
- `方案偏离检测规则参考.md`：7 条偏离规则的详细描述
- `FDA_FAERS_数据参考.md`：FAERS 数据格式和使用场景
- `MedDRA_层级结构参考.md`：五级层级结构和 27 个 SOC
- `PubMed_文献检索参考.md`：API 使用方法、检索策略

### 5.1 Git 版本控制——如何管理代码

**我用了 Git 来管理整个项目的版本，共 4 个有意义的 commit。**

大家看 git log：

```

ea043e8 Update: requirements.txt/Dockerfile/docker-compose/ECharts/配色/数据下载

551a33e Initial commit: AE Sentinel - 药物临床试验不良事件智能监测平台
```

**我的 Git 工作流**：
1. **第一次提交**时就把项目骨架搭好（目录结构、核心代码、前端页面）
2. **第二次提交**专门修 bug，比如健康检查接口的响应格式跟前后端接口文档不一致，导致前端测试报错
3. **第三次提交**按开发计划书补全缺失项——requirements.txt、Docker 文件、ECharts 图表、配色修改
4. **第四次提交**重写面试逐字稿

**`.gitignore` 配置**排除了不该提交的文件：
- `__pycache__/`、`*.pyc` —— Python 编译缓存
- `data/*.db`、`data/chroma/` —— 运行时生成的数据库和向量库
- `keys.txt`、`.env` —— 密钥文件不能泄露
- `data/downloads/*.zip` —— 大型数据文件不提交

### 5.2 Docker 容器化——如何部署

**项目支持 Docker 一键部署**，配套了 `Dockerfile` 和 `docker-compose.yml` 两个文件。

**Dockerfile** 做的事：
```dockerfile
FROM python:3.10-slim          # 基于轻量 Python 镜像
COPY requirements.txt .        # 先拷贝依赖文件
RUN pip install -r requirements.txt  # 安装依赖
COPY backend/ frontend/ lib/ run.py ./  # 拷贝源码
CMD ["python", "run.py"]       # 启动命令
EXPOSE 8000                    # 暴露端口
HEALTHCHECK --interval=30s ... CMD curl -f http://localhost:8000/api/health
# 容器启动后每30秒自动健康检查
```

**docker-compose.yml** 编排了三个服务：
- `ae-sentinel`（核心应用，端口 8000）
- `chromadb`（向量数据库，端口 8001）
- `ollama`（本地 LLM，注释状态，按需启用）

### 5.3 lib/ 目录——离线依赖的作用

**`lib/` 目录是本项目的离线依赖包**，目的是在没有网络的环境（如药企内网服务器）也能直接运行。

里面包含三个库：

| 库名 | 作用 | 为什么需要 |
|------|------|-----------|
| `lib/jwt/` | PyJWT | JWT Token 签发和验证，用于用户登录认证 |
| `lib/pymysql/` | PyMySQL | MySQL 数据库驱动，当需要从 SQLite 切换到 MySQL 时使用 |
| `lib/multipart/` + `lib/python_multipart/` | Python-Multipart | 解析 HTTP 文件上传请求（知识库上传文档时用到） |

这些库通过 `run.py` 中的 `sys.path.insert(0, lib_dir)` 加载到 Python 路径，优先使用本地离线版本。如果 pip 已安装这些库，本地版本也不会冲突。

### 【A】智能体1：AE 智能编码

**先看第一个，也是整个系统的入口——AE 智能编码。输入一段口语化的症状描述，AI 自动输出标准医学术语编码、严重程度、是否属于 SAE。**

**演示步骤（约 2 分钟）：**

> 第一步：登录系统。在登录页面输入 `pv_user` / `123456`，点击登录。登录后默认进入"工作台总览"页面。

> 第二步：导入测试数据。在工作台总览页面，点击"导入10个模拟病例"按钮。系统会提示"成功导入 10 个病例"。这些病例覆盖了头痛、恶心、皮疹、肺炎、肝损伤等多种场景。

> 第三步：进入 AE 编码页面。点击左侧菜单"AE编码"，可以看到上方是编码输入表单，右侧是编码结果展示区，下方是编码记录列表。

> 第四步：手动输入一条 AE。在表单中填写：患者编号 `NSCLC-011`、访视日期选今天、药物名称 `XK-001`，AE描述中输入 `"患者出现免疫相关肺炎，CT显示间质性肺病，气促加重，收治入院"`，点击"编码分析"。

> 第五步：观察结果。右侧结果区会展示：
> - **MedDRA 编码**：间质性肺病（置信度显示百分比）
> - **严重度**：红色 badge 显示"重度"
> - **SAE 标志**：红色 badge 显示"是"
> - **SAE 标准**：红色标签显示"导致住院"
> - **"生成SAE报告"按钮**自动出现

> 第六步：点击下方的 AE 编码记录列表，可以看到刚才编码的结果。已被判定为 SAE 的记录后面会有红色"生成SAE"按钮。

大家看代码——[`backend/agents/ae_coder.py`](file:///d:/works/AIclass/agent/AEPD Sentinel/backend/agents/ae_coder.py)。核心函数 `process_ae` 做了三件事：

**第一步：同义词映射**。内置 30+ 医学同义词字典，口语化描述自动转为标准术语。"反胃→恶心"、"吃不下饭→食欲减退"、"发烧→发热"。

**第二步：严重性分级 + SAE 判定**。关键词驱动的规则引擎：出现"住院"、"收入院" → 自动判定为 SAE，严重度 severe；出现"影响睡眠"、"持续" → moderate；其余 → mild。

**第三步：预期性判断**。对比 `config.py` 中预设的"预期AE列表"（14 个常见不良反应），判断是否为 SUSAR（可疑非预期严重不良反应）。

### 【B】智能体3：SAE 报告自动生成

**当智能体1 判定某个 AE 为 SAE 后，智能体3 自动生成符合国际标准的 CIOMS-I 报告。**

**演示步骤（约 1 分钟）：**

> 第一步：在 AE 编码页面，找到刚才编码的 NSCLC-011 记录（已标红显示"是"），点击"生成SAE"按钮。系统提示"SAE报告已生成: SAE-xxxx"后自动跳转 SAE 报告页面。

> 第二步：在 SAE 报告列表页面，可以看到刚生成的报告。每条报告显示：报告编号、患者编号、AE描述摘要、状态（草稿/审核中/已提交）、截止日期。注意截止日期列——系统自动计算了 AE 开始日期 + 7 天，并用彩色 badge 显示剩余天数。

> 第三步：点击某条报告的"查看"按钮，弹出 SAE 报告详情模态框，展示 CIOMS-I 表的 20+ 字段——患者信息、AE信息、可疑药物信息、因果关系评估、报告人信息。注意"同类药物安全性信息"一栏，这是智能体3 自动检索的。

> 第四步：点击"导出"按钮，浏览器自动下载 Word 格式的 CIOMS-I 报告文件。

看 [`backend/agents/sae_report.py`](file:///d:/works/AIclass/agent/AEPD Sentinel/backend/agents/sae_report.py)。`generate_sae_report` 函数做了：①从 AE 记录提取信息；②填充 CIOMS-I 表 20+ 字段；③计算报告截止日期（7天/15天）；④检索同类药物安全性信息。

导出功能在 [`backend/services/export_service.py`](file:///d:/works/AIclass/agent/AEPD Sentinel/backend/services/export_service.py) 实现，支持 Word、JSON、PDF 三种格式。

### 【C】智能体2：方案偏离识别

**这个智能体自动发现方案偏离——比如患者该来的访视没来、该做的检查没做。**

**演示步骤（约 1 分钟）：**

> 第一步：点击左侧菜单"方案偏离"，进入偏离管理页面。

> 第二步：页面上方是三个统计卡片——严重偏离、一般偏离、已解决的数量。

> 第三步：中间是偏离记录列表，每条显示偏离编号、患者、类型、严重程度（红色=严重、黄色=一般）、描述、状态（开放/待处理/已解决）。对于未解决的偏离，可以点击"解决"按钮。

> 第四步：点击"解决"按钮，弹出解决方案模态框。填写解决方案（如"已联系研究者确认访视日期无误"）、处理人、已采取措施，点击"确认解决"。偏离状态变为"已解决"。

偏离规则在 [`backend/core/database.py`](file:///d:/works/AIclass/agent/AEPD Sentinel/backend/core/database.py) 的 `init_db()` 中预置。严重程度分 major 和 minor，比如访视超窗 6 天（阈值 3 天）就是重大偏离。

## 七、技术架构亮点

### 7.1 RAG 知识库

**系统不是瞎编的，所有回答都基于实际文档。** 我们搭建了专属的临床试验安全知识库，包含 MedDRA 层级结构、ICH GCP 指南、FAERS 数据格式、CIOMS-I 规范、偏离规则。知识库在 [`backend/services/rag_engine.py`](file:///d:/works/AIclass/agent/AEPD Sentinel/backend/services/rag_engine.py) 中实现，基于 ChromaDB，支持用户上传文档并自动向量化。

### 7.2 多智能体协作

与传统单一 AI 对话不同，5 个智能体各司其职。智能体1 判定为 SAE 后自动触发智能体3，智能体5 对所有产出进行合规校验，智能体4 在后台定期做信号分析。**每个智能体可以独立优化、独立替换，不会互相干扰。**

### 7.3 前端技术方案

按照开发计划书要求，前端采用**单 HTML 文件 + ECharts CDN** 方案，7 个页面全部内嵌在一个文件中，无需 npm 构建。配色方案为简约浅色风格，主色 `#2B579A`（专业蓝）。

## 八、项目收获与总结

好，五个核心功能都讲完了。最后说说**我在这个项目里的收获**：

### 1. 跨领域知识的学习能力

这个项目最大的挑战不是技术，而是**业务理解**。临床试验、不良事件、MedDRA 编码、SAE 报告、方案偏离——这些概念对学计算机的人来说完全陌生。我花了大量时间阅读 ICH GCP 指南、FDA FAERS 数据文档、MedDRA 层级结构，确保每个功能的设计都符合行业规范。**一个优秀的工程师不能只懂技术，还得能快速理解一个新领域的业务逻辑。**

### 2. 多智能体架构的设计思维

把复杂业务拆成 5 个独立智能体，职责清晰、接口明确。**解耦让系统更灵活，以后如果要换一个更先进的编码模型，只改智能体1 就行，其他 4 个不受影响。**

### 3. 从"能用"到"合规"的工程思维

做 AI 应用最容易犯的错误是只追求"能跑通"，但药物警戒系统不一样——**准确率不够、合规性不足，这个系统就没有价值**。同义词映射保证编码一致性、规则引擎保证偏离判定准确、合规智能体保证报告不超期——这些"工程化"的思考比调模型参数更重要。

### 4. 全栈能力的整合

这个项目从前到后都是我一手搭建的：FastAPI 后端 + 9 个 API 路由、SQLite 数据库（7张表）、ChromaDB 向量检索、5 个智能体、ECharts 图表前端、Docker 容器化部署、Git 版本管理。踩过的坑包括：FastAPI 版本兼容性、SQLite 的 LIMIT/OFFSET 参数化不支持、路由顺序冲突——这些实际工程问题不写代码是遇不到的，解决了之后对 Python 生态的理解就更深了。
